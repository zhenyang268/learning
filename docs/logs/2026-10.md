### 2026-10-29（四元数 `quaternion.hpp` 完成：9 个入口全部落地 + 验收升级到 160 项）

- **起因**：用户「完善 quaternion.hpp」。读完发现 9 个入口用户已全部写出**实现体**，
  但带 6 处 bug，其中 3 处**编译器直接拦下的**（编不过），3 处是**编得过但算错**的。
- **修掉的 6 处**：
  1. **`Rotate` 返回 3×3 矩阵** —— `return v_prime.ToMatrix();`，量纲错
     （把"旋转后的向量"当成"旋转矩阵"），且 `v_prime` 是纯四元数、归一化后 w=0 那维丢了。
     改为返回 `(r.x, r.y, r.z)` 的 **3×1 列向量**。
  2. **`Slerp` 用 `expr / std::sin(theta)`** —— 四元数**没有** `operator/(T)`
     （刻意的：q1/q2 有左右之分，提供 `/` 就有二义性），编不过。
     改成乘倒数 `* (1/sin)`，**不为这一处去加 operator/**。
  3. **`Nlerp` 缺短弧翻号** —— `q1 = -q0` 时 `(1-t)q0 + t·q1` 在 t=0.5 处得零向量 ⇒
     `Normalize` 抛异常。补 `if (Dot(q0,q1) < 0) b = -q1;`。
  4. **`AngleOf` 缺 `|w|` 翻号** —— 转 1.5π 返回 1.5π 而非最短的 0.5π。
     补 `ww = (w<0) ? -w : w`。
  5. **`FromAxisAngle` 用了 `DefaultTol<T>()`** —— 一是不存在单参版本（签名要求 `n`）编不过；
     二是**容差在这里没有正当性**：单位化是尺度不变的除法，极小的非零轴归一化后方向完全正确，
     容差会把合法输入误判成非法。改为精确 `norm == 0`。
  6. **异常类型 `std::runtime_error`** —— 它**不派生自 `std::logic_error`**，
     测试的 `ThrowsLogicError` 抓不到；语义上也错（那是"运行环境出问题"）。
     改为三分：形状/参数非法 → `invalid_argument`；定义域外（零四元数求逆）→ `domain_error`。
- **顺带补的**：`IsZero()` 成员（把"精确全零"这个判据只写一处，别在 Inverse/Normalize
  里各写一遍）；`ToMatrix` 注释里 `tr(R)` 的符号写反了（写 `1-2cosθ`，
  本文件的 R 构造下是 `1+2cosθ` —— 不影响代码，但会误导人，已订正）。
- **验收升级**：`demo/quat/quaternion.cpp` 从骨架的 59 项 → **160 项**，
  `[P2]–[P10]` 全部换成真判据，新增四段：
  - **[D] 逆与归一化**（8 条）：**左右逆都测**（四元数不交换，只测一边漏一半代数）；
    用**非单位** q（|q|=√30）并断言 `q⁻¹ != q*`（差是 O(1)，专抓"写死单位四元数"）。
  - **[E] 轴角与矩阵**（16 条）：`FromAxisAngle` 半角/非单位轴/θ=0/θ=π；
    `ToMatrix` 逐格对拍解析式 + `RᵀR=I` + `det R=1` + 内部归一化；
    `FromMatrix` **四分支各自走到**（绕 x/y/z 转 π 分别命中分支 2/3/4，
    只测 R=I 会让 tr=3 永远走分支 1，是无效判据）；
    `Rotate` 与 `ToMatrix()*v` 对拍（两条独立路径）+ 保长 + 轴上不动 + `q`/`-q` 同结果。
  - **[F] 角度与插值**（16 条）：`AngleOf` 最短表示 / 小角 1e-6 / 非单位 q；
    `Slerp` 端点 / 单位长 / **匀速性 ptp ≤ 1e-4** / **短弧 0°→350° 中点 = 5°** / 退化无 NaN；
    `Nlerp` 端点 / 单位长 / `Nlerp(q,-q)` 不爆 / **反向判据：确实不匀速**（防以后被"优化"成 Slerp）。
  - **[G] 契约**（7 条）：零四元数 / 零轴 / 非 3×3 / 非 3×1 的错误类型各自精确到子类。
- **注入对照（四次，均回滚 + shasum 验过）**：

    `[C11]`（反自同构）、`[C13]`（同轴相加）全部仍绿** —— 它们对"整体符号翻转"不敏感。

### 2026-10-29（新增 `docs/math-to-code.md` —— 数学对象 → 代码形态的映射规则）

- **起因**：用户拿到一份「数学定理/公式怎么变成代码」的 T1–T5 分类稿（可计算公式 / 恒等式 /
  推导工具 / 算子 / 几何恒等式）让 agent 捋；捋完要求「整合一下把这一套也写成文档」。
- **诊断出的三个结构问题**：
  1. **按"对象"分类必然重叠** —— 分部积分同属 T2 与 T3，散度定理同属 T2 与 T5。
     根因：**对象与代码形态不是函数关系**，同一对象在不同位置有三种落点。
  2. **第一刀该切离散化，不是切定理** —— 同一泊松方程，FDM 一次都不用分部积分，FEM 必须用一次。
     离散化决定哪些定理进代码路径。
  3. **分类的真正产出不是标签而是判据** —— 说不出"给我哪条可执行判据"的对象不该进实现清单。
- **产出** `docs/math-to-code.md`（约 200 行）：
  - §0 为什么不用按对象分类（附分部积分在 1D 泊松里的三个落点）
  - §1 **离散化第一刀**：FDM/FEM/FVM/谱/MC 五策略 × 是否要分部积分、是否要积分、几何适应性；
    并给"约束 → 选择"的条件句（不是建议，是推论）
  - §2 **用法四层 L1–L4**（生成/装配/判据/叙述），允许一格多标；只有 L3/L4 标签的对象
    **不该进实现清单**
  - §3 **有无截断误差 = L1/L2 的硬分界**：有 → 验收敛阶（h 至少减半三次）；没有 → 只验
    "两边差在舍入级别"，**不许当成 `O(h^p)`**
  - §4 映射表 13 行，每行强制带「条件 + 数字」判据
  - §5 三条结构性事实：① Thomas / CG / CSR **不该捆成一件**（分别验格式精度、迭代行为、访存），
    ② **1D 等距线性元不需要 Gauss 积分**（`K = (1/h)·tridiag(-1,2,-1)`，手推更快），
    ③ **Gauss–Legendre 的节点是算法不是公式**（Golub–Welsch，可复用 `eigen`）
  - §6 可复用 prompt：**环境部分故意不写死"已有/没有"**，改为"先读 `dev-progress.md` §0 + `ls src/` 自行核实"，

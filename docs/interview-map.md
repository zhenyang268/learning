# interview-map.md — 三方向 × 学科 × 档位要求

> **定位**：只回答**「为了某个方向的面试，每条学科线要到哪一档」**。
> **不写**：具体怎么学、什么顺序 —— 那些在 `docs/baseline-levels.md`（档位定义）与 `NOW.md`（做什么）。
> **不写**：简历怎么写 —— 本文只给**档位要求**与**证据缺口**。
>
> **本文与 `baseline-levels.md` 的关系**：
> `baseline-levels.md` 定义「0~90 每档长什么样」；**本文只说「某个方向要求哪一档」**。
> 档位的判据一律引用 `baseline-levels.md` 的编号（M-E1、C-L3…），**不重复定义**。

---

## 0. 为什么需要这张表

**同一个学科，不同方向要求的档位不同。** 这是最容易误判的地方 —— 有人按「数学要学到很深」
去啃证明，结果发现目标岗位只要求数学 60、工程 80。

**核心规律（三个方向通用）**：

> **面试筛的是「工程能落地」，不是「学习有多深」。**
> 除了研究型岗位，**几乎没有任何方向要求数学 80+**；
> 但**所有方向都要求工程至少 60，其中两个方向要求 80**。

## 1. 三个方向 × 四条线 的档位矩阵

**图例**：`60` = 必备最低 · `80` = 决定胜负 · `—` = 不做要求 · `★` = 该方向的核心

| 学科线 | **C++ 后端 / 服务器** | **算法工程向测开** | **计算机图形学** |
|---|:--:|:--:|:--:|
| **数学（学习）** | 60 · | **60** | **60** |
| **数学（工程）** | 40（够用即可） | **60** | **60** |
| **数学物理（学习）** | — | — | 60（渲染方程那块） |
| **数学物理（工程）** | — | — | 40 |
| **CG（学习）** | — | — | **60** |
| **CG（工程）** | — | — | **80** ★ |
| **CS（学习）** | **80** ★ | **80** ★ | 60 |
| **CS（工程）** | **80** ★ | **80** ★ | 60 |

**三句话读法**：

1. **CS 是唯一三条线都要的学科** —— 因为它是「工程能力」的载体。
2. **CG 方向的胜负在 CG 工程 80**，数学只要 60（够读懂渲染方程）。
3. **测开方向的胜负在 CS 工程 80 + 数学工程 60**（能吃透数值正确性）。

## 2. 逐方向详解

### 2.1 C++ 后端 / 服务器

**岗位画像**：写服务端组件 —— RPC、存储、并发、性能。**不看数学推导，看系统能力。**

#### 要求矩阵（引用 `baseline-levels.md` 编号）

| 学科线 | 档位 | 具体要求（挑该档里最关键的） |
|---|---|---|
| **CS 学习** | **80** ★ | `S-L1..L4` 全部 60 **+ 80 档加问**：①写策略何时反转 ②NUMA 新问题 ③大页/COW ④协程 vs 线程（谁在调度）⑤无锁除了 ABA 还有什么坑 ⑥内存模型强弱 |
| **CS 工程** | **80** ★ | `S-E1..E6` 全过 **+ `S-E7..S-E10`**：规模化痕迹（1e3→1e6）· 性能归因到根因 · **故障注入** · 设计文档 |
| **数学 学习** | 60 | 只要 `M` 线的**概率三件 + L² 基础**（段 1–2），够读懂「一致性哈希为什么均匀」这类问题 |
| **数学 工程** | 40 | **不需要**。会用现成库（哈希/CRC/压缩）即可 |

#### 核心证据（面试直接讲的三件）

| 证据 | 现状（2026-10-28 实测） | 要补什么才到 80 |
|---|---|---|
| **Raft（Go，Lab 2A–2D + Lab3 kvraft）** | ✅ **已完成**（50 个 `.go`） | 见 §2.1b —— **算法能说，工程还差 80** |
| **cppraft v1.0**（`learning-408/raft/craft`） | ◐ **骨架很完整**：16 源文件 / **1067 行** / C++20 + gRPC + Protobuf + Boost.Asio + **Dockerfile + docker-compose（3 容器 + 固定 IP + NET_ADMIN）** + GoogleTest + pytest。**但测试极薄**（unit `test_storage.cpp` 30 行、system `test_cluster_bootstrap.py` 7 行） | **测试是最大短板** —— 有框架没内容 |
| **CSAPP / CS144 / jos** | ◐ 读过为主 | 挑**一个**做实质修改（§4.3 分界：读 vs 改） |

> **⚠️ cppraft 有一处待修**：目录里有 `docker-compose.ymlnjTz5h`（**疑似复制粘贴残留的坏文件**，
> 1316 B，与 `docker-compose.yml` 1515 B 并存）。会让人误以为工程不洁 —— **提交前删掉**。

#### 2.1b Raft 是「算法 60 / 工程 40」的典型 —— 怎么补到 80

> **用户原话**：「raft 这种就是算法能说，但是工程要求 80 分的」。
> **判断成立，而且比预想的更准。** 实测确认：Go 版 Lab 2A–2D + Lab3 全过 ⇒ **算法 60~70**（能应对追问）；
> C++ 版有像样的工程骨架（Docker + gRPC + 双测试框架）⇒ **工程框架分不低**，
> **但测试内容几乎为零 ⇒ 工程实际只有 40。**

**但工程侧还差在哪**（`S-E1..S-E10` 逐条对）：

| 检查点 | 现状 | 差距 |
|---|---|---|
| `S-E1` 并发正确性 | ✅ Go 版过 race detector（Lab 要求） | **但没记录踩过哪个 race** —— 80 要求「真实踩过的 bug + 复现 + 修法」 |
| `S-E2` 内存与性能 | ❌ | 没做过「Raft 的日志持久化 fsync 开销」这类量化 |
| `S-E3` 工程化 | ◐ **cppraft 框架齐全**（Docker/gRPC/CMake/GoogleTest/pytest） | **但测试只有 30 + 7 行** —— 有壳无肉 |
| `S-E7` 规模化 | ❌ | 测过 5 节点，**没测过** 100 client / 大量日志 / 慢节点 |
| `S-E8` 性能归因 | ❌ | 不知道 Raft 的**瓶颈在哪**（网络？磁盘？锁？） |
| `S-E9` 故障注入 | ◐ | `labrpc` 能模拟网络分区，**但没主动设计过故障场景矩阵** |
| `S-E10` 设计文档 | ◐ | cppraft 有 README（含 9 条待修点、Go/C++ 逐项对照）—— **接近够格** |

**⇒ 从「工程 40」补到 80，缺的是这四件**（按性价比排序）：

1. **把测试写实**（`S-E1` + `S-E3`）—— **当前最大短板**：
   unit 只有 `test_storage.cpp` 30 行、system 只有 `test_cluster_bootstrap.py` **7 行**。
   **至少补到**：存储层的边界（部分写/损坏/空日志）、Raft 的核心不变量
   （选举安全性、日志匹配、领导完备性）、以及**一个网络分区场景的端到端**。
2. **故障注入矩阵**（`S-E9`）—— 主动列场景：网络分区（少数派/多数派）、
   消息乱序/丢失/重复、节点崩溃重启、时钟跳跃。**每个场景给「期望行为 + 实际结果」。**
   **cppraft 有 `docker-compose` + `NET_ADMIN`，正好能做真网络分区** —— 这是天然优势。
3. **规模化 + 归因**（`S-E7/E8`）—— 把节点数/客户端数/日志长度扫一遍，
   给出**吞吐 vs 规模**曲线，并**归因**瓶颈（我猜是 fsync，但必须测）。
4. **真实 race 记录**（`S-E1` 的 80 要求）—— 回看当时 `go test -race` 抓到过什么，
   写成一个 case。**哪怕只有一个。**

> **⚠️ 一句实话**：Lab 过与「工程 80」的差距**不在代码量，在「有没有做过测量与故障设计」**。
> cppraft 的 Docker + gRPC + 双测试框架已经把「工程骨架」这一层做完了（这比多数人强），
> **缺的是往里填内容** —— 而填测试与故障注入**不需要改核心逻辑**，性价比最高。

### 2.2 算法工程向测试开发

**岗位画像**：为算法/算子建测试与质量保障 —— 数值正确性、性能基线、归因、可复现。
**核心是「测得出、归得清」，不是「跑得快」。**

#### 要求矩阵

| 学科线 | 档位 | 具体要求 |
|---|---|---|
| **数学 学习** | **60** | 十段里至少要 `段 1–5`（概率 / L² / 泛函 / Sobolev / 变分）—— **因为要判断数值方法的正确性** |
| **数学 工程** | **60** ★ | `M-E1..M-E6` 全过。**重点是 `M-E2`（判据独立于实现）与 `M-E4`（精度边界说得成因）** |
| **CS 学习** | **80** ★ | `S-L4` 并发与同步是命门 + 80 档加问（无锁的坑、内存模型） |
| **CS 工程** | **80** ★ | `S-E1..E6` + `S-E7..S-E10`。**`S-E1`（并发正确性 + TSan）是测开岗最核心证据** |

#### 核心证据

| 证据 | 现状 | 优先级 |
|---|---|---|
| **`learning-benchmark/`（微基准与归因框架）** | ✅ **设计闭合**（10 提交，7 份文档）/ ❌ **代码零** | **最高** —— 这就是岗位的"作品集" |
| **`graphics/`（17 ctest，SVD 266 项）** | ✅ 已完成 | 已有；需整理成「判据设计」的讲述 |
| **Raft** | ✅ 算法过 | 对测开岗，**Raft 的价值是「故障注入」（`S-E9`）**，不是 Raft 本身 |

#### 这个方向的档位陷阱

> **数学工程 60 的关键不是「会推公式」，是「知道容差怎么定」。**
> 具体到 `baseline-levels.md` 的 `M-E4`：能说出 `A^H A` 路线为什么精度只有 `sqrt(eps)`。
>
> **测开面试一定会问**：「你怎么知道两个浮点结果算相同？」—— 这题答不出，
> 前面所有工程能力都不作数。

### 2.3 计算机图形学

**岗位画像**：渲染 / 几何处理。**要能实现经典算法 + 做白炉验证 + 定位伪影根因。**

#### 要求矩阵

| 学科线 | 档位 | 具体要求 |
|---|---|---|
| **CG 学习** | **60** | `C-L1..C-L8` 全过。**核心是 `C-L3`（渲染方程）与 `C-L4`（蒙特卡洛）** |
| **CG 工程** | **80** ★ | `C-E1..C-E7` 全过 **+ `C-E8..C-E11`**：收敛速率实测 · 性能归因到行 · 鲁棒管线 · 可复现渲染 |
| **数学 学习** | **60** | `段 1–2`（概率 + L²/傅里叶）是硬需求 —— **渲染 = 积分 + 采样** |
| **数学 工程** | 60 | `M-E2/M-E4`（判据独立 + 精度边界）—— 渲染的容差问题与此同构 |
| **数学物理** | 60（学习）/ 40（工程） | **只为读懂渲染方程的物理来源**（辐射度量学），不做数值 |
| **CS 学习/工程** | 60 | 够用：会写 C++、会用 CMake、能看 profiler。**不需要 80** |

#### 核心证据

| 证据 | 现状 | 缺口 |
|---|---|---|
| **`pyapps` G1–G6 / R1–R6**（球面 / 旋转，12 脚本 + 13 图） | ✅ 已完成 | 只能算 **CG 工程 40** —— 有几何和旋转，**没有渲染** |
| **`quat` / `so3`**（C++ 实现） | ◐ quat 有 10 处 throw | 补完 → 支撑 `C-E3` |
| **BRDF / 白炉 / 路径追踪** | ❌ **完全零** | **这是 CG 方向最大的缺口** —— `C-E1`/`C-E2` 是核心项 |

#### 这个方向的档位陷阱

> **CG 的 60→80 分界不在「会写 shader」，在「能证明它是对的」。**
>
> - **60**：能实现 Lambert/GGX，出图好看
> - **80**：**白炉测试能量误差 < 1%** + **方差随样本数下降斜率 ≈ -0.5** + **profiling 定位到行**
>
> **「出图好看」是最容易自我欺骗的一条** —— 所以 `C-E5` 要求「图能自证」。

## 3. 三方向共用的「必答问题」

**不管投哪个方向，这三个问题都会出现。** 它们跨学科线，所以单独列。

| # | 问题 | 对应档位 | 答不出会怎样 |
|---|---|---|---|
| Q1 | **你这个数字的机器/规模/容差是什么？** | 工程 60 的入场券（`baseline-levels.md` §0.4） | 数字全废（反例 `N1`） |
| Q2 | **什么输入会让它错？你怎么发现的？** | 工程 60 的失败模式 | 说明只测了 happy path（反例 `N3`） |
| Q3 | **为什么用这个方案而不是那个？** | 工程 80 的第一层追问（§0.8） | 停在 60 |

**Q3 的进阶版（80 档的核）**：

> **「什么条件下它会失效？」** —— 答不出第三层，就是 60。

## 4. 现状对照：三条线各自离目标差什么

> 只列**关键缺口**，不列全部（全部见 `baseline-levels.md` 各节「现状」列）。

### 4.1 C++ 后端 / 服务器 → 目标：CS 工程 80

| 已有 | 缺口 | 差几档 |
|---|---|---|
| Raft 算法（Go，Lab1–3 全过，50 个 .go） | 真实的 race 记录 + 规模化数据 | **算法 60~70，基本够** |
| **cppraft v1.0**（16 源文件 1067 行，Docker + gRPC + GoogleTest + pytest） | **测试只有 30 + 7 行** · 故障场景矩阵 · 性能归因 | **工程 40 → 80，四件事** |
| jos / cs144 / csapp | 「读过」→「改过」 | 学习 60 → 工程 60 |
| — | **规模化痕迹（`S-E7`）** | **最大缺口**，个人项目最难补 |

> **好消息**：cppraft 的 Docker + `NET_ADMIN` 让**真网络分区**成为可能 —— 这是多数人
> 做 Raft 项目做不到的（他们只能用模拟库）。**这是可以主动讲的差异点。**

### 4.2 算法工程向测开 → 目标：数学工程 60 + CS 工程 80

| 已有 | 缺口 | 差几档 |
|---|---|---|
| `graphics/` 17 ctest（SVD 266 项） | 整理成「判据设计」的讲述 | 工程 **已达 60**，差「讲清」 |
| `learning-benchmark/` 设计闭合 | **代码零**（M1 未开工） | 工程 0 → 需做到 60 |
| 数学（段 0 推进中） | 段 1–5 未到 | 学习 60 未达 |
| TSan / ASan 经验 | 未见记录 | `S-E1` 未达 |

**⇒ 这个方向的路径最短**：`graphics` 的判据资产已经很强，只差「benchmark 代码」与「讲清」。

### 4.3 CG → 目标：CG 工程 80

| 已有 | 缺口 | 差几档 |
|---|---|---|
| pyapps G1–G6 / R1–R6（12 脚本 13 图） | 只有几何+旋转，**无渲染** | 40 |
| `quat` / `so3` C++ | quat 10 处 throw 待填 | 40 → 60 |
| **BRDF / 白炉 / 路径追踪** | **完全零** | **0 → 这是硬门槛** |
| 收敛速率 / profiling | 无 | 80 要求的核心 |

**⇒ 这个方向缺口最大**：核心项 `C-E1`/`C-E2` 是从零开始。

## 5. 一句话

> **三个方向的共同点：数学 60 够，工程要 80。**
> **C++ 后端**：CS 工程 80（Raft 补四件事）· **测开**：数学工程 60 + CS 工程 80（benchmark 补代码）
> · **CG**：CG 工程 80（BRDF/白炉/路径追踪 从零）
>
> **面试筛的从来不是「学得多深」，是「工程能不能落地、边界知不知道、数字有没有条件」。**

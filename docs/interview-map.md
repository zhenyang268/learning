# interview-map.md — 三方向 × 学科 × 档位要求

> **定位**：只回答**「为了某个方向的面试，每条学科线要到哪一档」**。
> **不写**：具体怎么学、什么顺序 —— 那些在 `docs/baseline-levels.md`（档位定义）与 `NOW.md`（做什么）。
> **不写**：简历怎么写 —— 本文只给**档位要求**与**证据缺口**。
>
> **本文与 `baseline-levels.md` 的关系**：
> `baseline-levels.md` 定义「0~90 每档长什么样」；**本文只说「某个方向要求哪一档」**。
> 档位的判据一律引用 `baseline-levels.md` 的编号（M-E1、C-L3…），**不重复定义**。

---

## 0. 为什么需要这张表

**同一个学科，不同方向要求的档位不同。** 这是最容易误判的地方 —— 有人按「数学要学到很深」
去啃证明，结果发现目标岗位只要求数学 60、工程 80。

**核心规律（三个方向通用）**：

> **面试筛的是「工程能落地」，不是「学习有多深」。**
> 除了研究型岗位，**几乎没有任何方向要求数学 80+**；
> 但**所有方向都要求工程至少 60，其中两个方向要求 80**。

## 2. 逐方向详解

### 2.1 C++ 后端 / 服务器

**岗位画像**：写服务端组件 —— RPC、存储、并发、性能。**不看数学推导，看系统能力。**

#### 要求矩阵（引用 `baseline-levels.md` 编号）

| 学科线 | 档位 | 具体要求（挑该档里最关键的） |
|---|---|---|
| **CS 学习** | **80** ★ | `S-L1..L4` 全部 60 **+ 80 档加问**：①写策略何时反转 ②NUMA 新问题 ③大页/COW ④协程 vs 线程（谁在调度）⑤无锁除了 ABA 还有什么坑 ⑥内存模型强弱 |
| **CS 工程** | **80** ★ | `S-E1..E6` 全过 **+ `S-E7..S-E10`**：规模化痕迹（1e3→1e6）· 性能归因到根因 · **故障注入** · 设计文档 |
| **数学 学习** | 60 | 只要 `M` 线的**概率三件 + L² 基础**（段 1–2），够读懂「一致性哈希为什么均匀」这类问题 |
| **数学 工程** | 40 | **不需要**。会用现成库（哈希/CRC/压缩）即可 |

#### 核心证据（面试直接讲的三件）

| 证据 | 现状（2026-10-28 实测） | 要补什么才到 80 |
|---|---|---|
| **cpporaft（`learning-408/raft/craft`，C++ 版）** | ✅ **比原以为的强得多**：16 源文件 / 1067 行核心 + **7 个脚本共 344 行**（`inject_fault.sh` 115 行含 delay/loss/clear/partition/heal/kill/restart）· C++20 + gRPC + Protobuf + Boost.Asio · Docker 3 容器固定 IP + `NET_ADMIN` · **五场景实测**（S1 正常 → S5 重启）· **2C 持久化**（临时文件→fsync→rename→fsync(dir) 原子写） | **测试代码仍薄**（unit 30 行 / pytest 7 行）—— **五场景是靠手工脚本验证的，没沉淀成自动化** |
| **Raft（Go，Lab 2A–2D + Lab3 kvraft）** | ✅ **已完成**（50 个 `.go`） | 算法 60~70，够 |
| **CSAPP / CS144 / jos** | ◐ 读过为主 | 挑**一个**做实质修改（§4.3 分界：读 vs 改） |

#### 2.1b Raft 是「算法 60 / 工程 40」—— **实测修正：工程其实已到 60~70**

> **用户原话**：「raft 这种就是算法能说，但是工程要求 80 分的」。
> **我第一轮判断为「工程 40」，实测后必须更正。** 依据是 `craft` 仓的三次提交：

**已做实的（超出一般课程项目）**：

| 项 | 证据 |
|---|---|
| **真故障注入** | `scripts/inject_fault.sh` **115 行**，支持 `delay / loss / clear / partition / heal / kill / restart`；Docker + `NET_ADMIN` ⇒ **真 tc/iptables**，不是模拟库 |
| **五场景实测记录** | S1 正常 → S2 加 20ms 抖动 → S3 断 node2（`{1,3}` 继续 72→73，node2 停 56，heal 后 10s 追到 119）→ S4 kill leader（node2 接任，applied=155）→ **S5 重启（applied=343 vs 205/206，暴露状态机重复 apply）** |
| **从故障推出需求** | **S5 直接导出 2C 持久化**，并定出验收标准「restart 后 applied 不超过真实命令数」—— **这是「测出问题→改设计」的闭环** |
| **持久化正确性** | `RaftStorage`：临时文件 → `fsync` → `rename` → **`fsync(dir)`**。注释写明「rename 同文件系统原子，但**目录 fsync 才能保证 rename 本身落地**」—— 这个细节多数人不知道 |
| **只存该存的** | `PersistentState{term, voted_for, logs}` 只存论文 Figure 2 的 persistent state；`commitIndex`/`lastApplied` 可由「日志+重选」重建，`nextIndex`/`matchIndex` 只有 leader 用 ⇒ **不存** |

**还差什么才到 80**（`S-E1..E10` 对完，只剩两条半）：

| 检查点 | 现状 | 差距 |
|---|---|---|
| `S-E3` 工程化 | ✅ Docker/CMake/脚本/conf 齐全 | — |
| `S-E9` 故障注入 | ✅ **五场景 + 脚本化** | — |
| `S-E10` 设计文档 | ◐ README 有，提交信息写得很实 | 略欠系统化 |
| **`S-E1` 自动化并发正确性** | ❌ **五场景是手工跑的**，pytest 只有 7 行 | **最大缺口**：把手工场景变成**可重复的自动化测试** |
| **`S-E7/E8` 规模化 + 归因** | ❌ | 没扫过节点数/客户端数/日志长度，**没说清瓶颈在哪** |
| `S-E2` 内存与性能 | ❌ | fsync 开销没量化 |

**⇒ 从「60~70」到 80，缺的其实只有两件事**（不是四件）：

1. **把手工场景沉淀成自动化**（`S-E1` + `S-E3`）——
   现在 `inject_fault.sh` 能跑，但**结果要人看**；把它变成 pytest 断言，
   每条场景**自动判 PASS/FAIL**。这是**从「我测过」到「可回归」的关键一步**。
2. **规模化 + 归因**（`S-E7/E8`）—— 节点数 3/5/7、客户端 1/10/100、日志长度 1k/10k/100k
   各扫一遍，给吞吐曲线 + **瓶颈归因**（fsync？网络？锁？）。**必须有数字。**

> **⚠️ 我上一轮的判断失误，原因值得记**：我看了 `learning-408/README.md` 的描述
> （「`craft/` 为 C++ 版 craft v1.0」）就下了结论，**没有进仓看 git log**。
> 实际上那个 README 停在 v1.0，而仓里已经到「2C 持久化」了。
> **教训：判断项目成熟度必须看 `git log` 与提交信息，不能只看 README。**

### 2.2 算法工程向测试开发

**岗位画像**：为算法/算子建测试与质量保障 —— 数值正确性、性能基线、归因、可复现。
**核心是「测得出、归得清」，不是「跑得快」。**

#### 要求矩阵

| 学科线 | 档位 | 具体要求 |
|---|---|---|
| **数学 学习** | **60** | 十段里至少要 `段 1–5`（概率 / L² / 泛函 / Sobolev / 变分）—— **因为要判断数值方法的正确性** |
| **数学 工程** | **60** ★ | `M-E1..M-E6` 全过。**重点是 `M-E2`（判据独立于实现）与 `M-E4`（精度边界说得成因）** |
| **CS 学习** | **80** ★ | `S-L4` 并发与同步是命门 + 80 档加问（无锁的坑、内存模型） |
| **CS 工程** | **80** ★ | `S-E1..E6` + `S-E7..S-E10`。**`S-E1`（并发正确性 + TSan）是测开岗最核心证据** |

#### 核心证据

| 证据 | 现状 | 优先级 |
|---|---|---|
| **`learning-benchmark/`（微基准与归因框架）** | ✅ **设计闭合**（10 提交，7 份文档）/ ❌ **代码零** | **最高** —— 这就是岗位的"作品集" |
| **`graphics/`（17 ctest，SVD 266 项）** | ✅ 已完成 | 已有；需整理成「判据设计」的讲述 |
| **Raft** | ✅ 算法过 | 对测开岗，**Raft 的价值是「故障注入」（`S-E9`）**，不是 Raft 本身 |

#### 这个方向的档位陷阱

> **数学工程 60 的关键不是「会推公式」，是「知道容差怎么定」。**
> 具体到 `baseline-levels.md` 的 `M-E4`：能说出 `A^H A` 路线为什么精度只有 `sqrt(eps)`。
>
> **测开面试一定会问**：「你怎么知道两个浮点结果算相同？」—— 这题答不出，
> 前面所有工程能力都不作数。

### 2.3 计算机图形学

**岗位画像**：渲染 / 几何处理。**要能实现经典算法 + 做白炉验证 + 定位伪影根因。**

#### 要求矩阵

| 学科线 | 档位 | 具体要求 |
|---|---|---|
| **CG 学习** | **60** | `C-L1..C-L8` 全过。**核心是 `C-L3`（渲染方程）与 `C-L4`（蒙特卡洛）** |
| **CG 工程** | **80** ★ | `C-E1..C-E7` 全过 **+ `C-E8..C-E11`**：收敛速率实测 · 性能归因到行 · 鲁棒管线 · 可复现渲染 |
| **数学 学习** | **60** | `段 1–2`（概率 + L²/傅里叶）是硬需求 —— **渲染 = 积分 + 采样** |
| **数学 工程** | 60 | `M-E2/M-E4`（判据独立 + 精度边界）—— 渲染的容差问题与此同构 |
| **数学物理** | 60（学习）/ 40（工程） | **只为读懂渲染方程的物理来源**（辐射度量学），不做数值 |
| **CS 学习/工程** | 60 | 够用：会写 C++、会用 CMake、能看 profiler。**不需要 80** |

#### 核心证据

| 证据 | 现状 | 缺口 |
|---|---|---|
| **`pyapps` G1–G6 / R1–R6**（球面 / 旋转，12 脚本 + 13 图） | ✅ 已完成 | 只能算 **CG 工程 40** —— 有几何和旋转，**没有渲染** |
| **`quat` / `so3`**（C++ 实现） | ✅ quat 已全部落地（160 项判据），so3 有专项用例 | `C-E3` 剩余缺口是 **BVH / 相机层级**，不在四元数 |
| **BRDF / 白炉 / 路径追踪** | ❌ **完全零** | **这是 CG 方向最大的缺口** —— `C-E1`/`C-E2` 是核心项 |

#### 这个方向的档位陷阱

> **CG 的 60→80 分界不在「会写 shader」，在「能证明它是对的」。**
>
> - **60**：能实现 Lambert/GGX，出图好看
> - **80**：**白炉测试能量误差 < 1%** + **方差随样本数下降斜率 ≈ -0.5** + **profiling 定位到行**
>
> **「出图好看」是最容易自我欺骗的一条** —— 所以 `C-E5` 要求「图能自证」。

## 5. 面试深度问答（跨方向通用，**答不出就是 60**）

> 面试官**不会让你推 SVD 收敛证明**，而是问「为什么」。
> 下面每条都是「问题 → 本仓有什么可答」，可直接背。

| 问题 | 本仓有什么可答 |
|---|---|
| **为什么 Cholesky 不用 LU？** | SPD ⇒ 只有一半自由度（`L` 存一半）、**无需选主元**、`O(n³/6)` vs `O(n³/3)` |
| **Slerp 为什么是测地线？线性插值坏在哪？** | S³ 上大圆；**Lerp 不走球面 ⇒ 角速度不匀 + 长度缩短 + 过近点时抖动**；`pyapps/rotation/R1–R6` 有实测图 |
| **CG 为什么要求 SPD？病态时为什么慢？** | 能量泛函 `Φ` 才有意义、Krylov 子空间正交性；**条件数 κ 决定收敛率 `√κ`** |
| **高斯积分为什么用勒让德根？n 点精确几次？** | **n 点精确 `2n−1` 次**多项式（自由度匹配）；根是 `P_n` 的零点 |
| **你的误差阶表斜率对不对？失败模式是什么？** | RK4 斜率 **≈ −4**（`h` 减半误差降 16 倍）；**失败模式：非辛格式能量单调漂移** |

**本仓特有的三条**（别人答不出来，因为要靠实测边界）：

| 问题 | 答 |
|---|---|
| **为什么你的 SVD 精度只有 `√eps`？** | 走 `AᴴA` 路线，**条件数被平方** ⇒ 小奇异值精度降到 `√eps`；所以可信线 `σ/σmax ≳ 1e-6` |
| **为什么你的闸门不保证「所有接口都被测过」？** | 闸门只保证**登记过的**入口被实例化，不保证全部被登记 —— 本仓实测漏了 4 个（`expm_pade` + `so3` 三个）。**主动讲这个反而加分**：说明你知道工具的边界 |
| **同一份代码支持 double/complex/dual，怎么保证没写错？** | 算法层零实复分支（差异只在 traits 特化）+ 每个域各实例化一次。**这个仓踩过 5 次「double 域 0 错掩盖 complex bug」** |

## 6. 明确不做（防范围蠕变）

| 不做 | 理由 |
|---|---|
| 重写 SVD / Autodiff | **本仓已完成且验收更严**（SVD 266 项 / backward 31 项含三方对拍），重做是浪费 |
| 完整 FEM | 只做 1D Poisson 最小闭环（赛道口径见 `eng-competency.md` §1.1） |
| 预条件子（ILU / AMG） | 只讲「解决什么」 |
| Ziggurat / KS 检验 / Q–Q 图 | 选做；`cdf(ppf(p))` 往返误差 `< 1e-8` 够用 |
| 任意长度 / 混合基 FFT | 只支持 2 的幂；非 2 幂走朴素 `O(n²)` |
| 工业级 SVD（双对角化 + 隐式 QR） | 现有 `AᴴA` 路线够讲清数值稳定性 |

**这些「不做」是主动选择，不是能力缺口。** 面试被问到就直说「知道它是什么、为什么难、
我的最小闭环到哪」—— 这比硬做一个半成品强。

## 7. 一句话

> **三个方向的共同点：数学 60 够，工程要 80。**
> **C++ 后端**：CS 工程 80（Raft 补四件事）· **测开**：数学工程 60 + CS 工程 80（benchmark 补代码）
> · **CG**：CG 工程 80（BRDF/白炉/路径追踪 从零）
>
> **面试筛的从来不是「学得多深」，是「工程能不能落地、边界知不知道、数字有没有条件」。**

## 0. 标尺

### 0.1 三档（**定义不在这里写，见 `baseline-levels.md` §0.2**）

> **本文与 `baseline-levels.md` 的分工已澄清（2026-10-28）**：
> **三档的定义只有一处真源 —— `baseline-levels.md` §0.2**（它同时给了学习侧与工程侧判据）。
> 本文**不再重写定义**，避免两份文档各说一套、日后漂移。
>
> 一句话记法（只是摘要，判据以真源为准）：
> **60 = 会用；80 = 知道它什么时候不灵，并能修；90 = 别人用你的。**
>
> **面试侧读法**：60 分 = 问原理和失败模式你能接住，且有代码和数字；
> 80 分 = 问边界、性能、根因，你有实战证据。

### 0.2 一条补充（比"有代码和数字"更严，本仓口径）

**数字不是证据，数字的适用条件才是证据。** 每个数字必须带三件：

> **条件**（机器 / 编译器与优化级 / 规模 / 容差 / 基线是什么）
> **+ 数字**（误差 / 收敛阶 / 迭代数 / 加速比 / 内存）
> **+ 失败模式**（什么输入会让它错、错成什么样、你怎么发现的）

- 反例：「CG 快 3.2×」——噪音，无法判断是否只是换了机器。
- 正例：「N=10⁵、float64、-O3、容差 1e-8、对比 Jacobi 预条件，迭代数 812 → 96，预条件耗时占比 7%」。

**这条是 60 与"我跑通了"的唯一分界。** 面试官不信任候选人的第一原因从来不是算法不会，而是数字没有条件。

### 0.3 60 分的"数字"合格线（每类各一条）

| 类 | 合格形态 |
|---|---|
| 正确性 | 误差**表**：每个 case 有实测值 + 参考值 + 判据（不是"和理论一致"） |
| 收敛 | 斜率对得上理论阶：RK4 ≈ 4、Verlet ≈ 2、CG 迭代数随 √κ 增长 |
| 性能 | 优化前后**同条件**对照；给加速比 + 瓶颈归因（带宽/缓存/指令） |
| 失败 | 列 2–3 个**会算错的输入**（近奇异 / 尺度悬殊 / 坐标奇异）+ 错成什么样 |

## 1. 四个赛道的 60 / 80

### 1.1 CAE / 数值仿真

**60 分检查点**

| # | 检查点 | 合格线 |
|---|---|---|
| 1 | **有限元链路（1D 全程）** | 从变分推出弱形式 → Gauss–Legendre 组装 → Dirichlet/Neumann 边界 → 稀疏系统 → CG 求解；能画出残差收敛曲线 |
| 2 | **稀疏线性代数** | CSR/CSC、SpMV；CG + Jacobi 预条件；能诊断"病态系统下 CG 为什么慢"，不收敛时知道先看什么 |
| 3 | **时间积分** | Euler/RK4/辛欧拉/Verlet；误差阶斜率对得上；能讲稳定性、刚性、能量漂移 |
| 4 | **数值验证习惯** | 每个模块有误差表 + 收敛曲线 + 失败模式说明；有单元测试 |

**80 分检查点**

| # | 检查点 | 合格线 |
|---|---|---|
| 5 | 非线性 | Newton 迭代 + 线搜索 + 收敛判据；能说清什么时候发散、怎么救 |
| 6 | 大规模稀疏 | GMRES/BiCGStab；ILU/AMG 预条件；能给"不同预条件子的收敛 + 内存"对比表 |
| 7 | 性能工程 | 热点并行化；profiling 定位访存瓶颈；给强/弱扩展性数字 |
| 8 | 工业工具链 | PETSc / SuiteSparse / Eigen 稀疏模块，至少一个能改能调 |

> **一句话**：60 = 能搭 1D 链路并诊断收敛；80 = 能在大规模稀疏系统上做预条件选型与并行调优。

### 1.2 HPC / 数值算子与性能工程

**60 分检查点**

| # | 检查点 | 合格线 |
|---|---|---|
| 1 | 稀疏算子 | CSR/CSC/COO、SpMV；能定量说清**访存不规则**的性能代价（对比稠密） |
| 2 | 迭代求解器 | CG、GMRES 的移植与调优；理解预条件的作用**和代价** |
| 3 | 性能分析 | 能用 profiling 定位瓶颈（缓存/带宽/循环）；至少一个多后端 benchmark 并解释拐点 |
| 4 | 并行基础 | OpenMP **或** CUDA 至少一个能写能调；MPI 了解通信与扩展性概念 |

**80 分检查点**

| # | 检查点 | 合格线 |
|---|---|---|
| 5 | 异构深度优化 | CUDA kernel 设计、shared memory、warp 级优化；GPU 传输/launch 开销的量化 |
| 6 | 多节点 | MPI 域分解、集合通信、强/弱扩展性曲线 |
| 7 | 稀疏求解深度 | Krylov 全家桶、AMG、稀疏直接法；能选型并说清为什么 |
| 8 | 性能可移植性 | 同一内核在 CPU/GPU 上的 roofline 分析与调优报告 |

> **一句话**：60 = 能写稀疏算子并调优单节点；80 = 能做多节点/GPU 的扩展性与 roofline 分析。

### 1.3 CAD / 计算几何与几何处理

**60 分检查点**

| # | 检查点 | 合格线 |
|---|---|---|
| 1 | 几何基础 | Bézier/B 样条/NURBS 入门：连续性、插值 vs 逼近；布尔运算、Delaunay、网格修复的**概念** |
| 2 | 几何数据结构 | 网格邻接/半边；空间划分（BVH/KD/八叉）；能实现简单求交与邻域查询 |
| 3 | 数值几何 | 矩阵/四元数变换、投影、**容差处理**；能诊断"两个面判相交但浮点不稳" |
| 4 | 内核认知 | OCCT/ACIS/Parasolid 至少了解一个的数据结构概念 |

**80 分检查点**

| # | 检查点 | 合格线 |
|---|---|---|
| 5 | 工业内核 | 能在 OCCT/ACIS/Parasolid 之一上做二次开发或模块开发 |
| 6 | 鲁棒几何 | 容差设计、退化处理、布尔运算的数值稳定性 |
| 7 | 网格处理 | 大规模网格质量评估、简化、参数化 |
| 8 | 规模 | 千万级网格的空间查询与几何处理性能 |

> **一句话**：60 = 能实现经典几何算法并处理容差；80 = 能在工业内核上做鲁棒模块。

### 1.4 图形 / 渲染

**60 分检查点**

| # | 检查点 | 合格线 |
|---|---|---|
| 1 | 变换与空间 | 矩阵/四元数/SLERP、相机、层级；空间划分（BVH/八叉/KD） |
| 2 | 着色与 BRDF | Lambert/Blinn–Phong；Cook–Torrance GGX 的 D/G/F；**能量守恒直觉**；GGX 重要性采样；**白炉测试** |
| 3 | 渲染管线 | 光栅化/z-buffer/透视校正；路径追踪基础 + **方差分析**；至少一种 shader 语言能读能改 |
| 4 | 性能意识 | 能讲清一个 render pass 的瓶颈在哪（带宽/overdraw/shader 复杂度） |

**80 分检查点**

| # | 检查点 | 合格线 |
|---|---|---|
| 5 | 工业管线 | PBR/IBL/GI/阴影/后处理中至少一个方向能独立开发 |
| 6 | GPU 性能 | 现代 GPU 架构、Vulkan/DX12、GPU profiling 与优化 |
| 7 | 大规模场景 | LOD/合批/遮挡剔除/千万级网格调优 |
| 8 | 神经渲染 | 3DGS/NeRF 的投影、排序、可微链路 |

> **一句话**：60 = 能实现经典光照并做白炉验证；80 = 能在工业引擎里做管线级性能优化。

### 三处**必须你自己确认**（我不替你断言）

1. **并行 benchmark 的资产在哪**。本仓 `graphics/src` 全库搜 `OpenMP|ISPC|CUDA|_mm256` **零命中**，
   但 **`learning/learning-benchmark/` 这个独立仓已存在**（2026-10-28 实测：10 次提交，
   设计全部闭合、**代码未开工**）。它的两条实测结论**直接约束 HPC 赛道判据**：
   - **硬件 PMU 不可用**（`unsupported p6 CPU model 183 no PMU driver`）⇒ `#3 性能分析`
     只能走**唯一变量对照实验**，**不能声称用了 perf 计数器**；
   - **不绑核**（WSL2 拓扑是合成的）⇒ `#4 并行` 能写能跑，但**多线程加速比不可引用**。

   ⇒ **HPC 60 的 #1/#2/#3 可真做，#4 只能算半个**（详见 `docs/baseline-levels.md` §5.3）。
2. **三个「Gauss」不是一回事**：`NaiveGaussSolve`（`demo/linalg/solve.cpp`，高斯消元）、
   Gauss–Bonnet（`demo/pyapps/sphere/octant.py`，曲率）、**Gauss–Legendre 求积（零行）**。
   上一版清单把前两个当成第三个，据此得出"可直接复用"——那是错的。
3. **岗位要求是市场事实，不是知识判断题**。不要用 agent 的判断替代抽样：取 20 个真实 JD，
   只记三列 —— **学历要求 / 是否明写"稀疏、预条件、MPI/GMRES、BRDF、BVH" / 是否要求专业对口**。
   三个频次出来，赛道可行性自己就清楚了，且面试时能反推对方团队在做什么。

## 4. 60 → 80 的通用差距（四赛道都适用）

| # | 差距 | 60 分的表现 | 80 分的证据形态 |
|---|---|---|---|
| 1 | 我实现了 → 我验证了边界 | 跑通经典 case | 退化 case 表 + 极端参数 + 失败模式对照 |
| 2 | 能跑 → 能调 | 能编译能出数 | profiling 报告 + 瓶颈归因 + 优化前后数字 |
| 3 | 单文件 demo → 能被人接手 | 自己能跑 | CMake + 依赖管理 + 单测 + 模块边界 + 文档 |
| 4 | 我做过 → 我能讲清为什么 | 复述流程 | 选型依据 + 失败教训 + 与工业工具的**对比** |
| 5 | 玩具规模 → 有规模化痕迹 | 小算例 | "规模上去后暴露了什么、怎么解决的"证据 |

> **80 分的"大规模痕迹"很难靠个人项目伪造** —— 这是这份文档里唯一无法靠自学补上的部分。
> 60 分可以完全靠自证，80 分通常需要一个真实场景。

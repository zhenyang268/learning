### 0.2 设计层（②）
- **进程是 OS 的"资源分配单位"与"调度单位"**：OS 管理的核心对象。
- **层级定位**：进程管理位于**内核态核心层**——向下驱动硬件（通过中断/特权指令），向上为所有程序提供运行抽象。
- **为什么需要"进程"这个抽象**：解决"多个程序如何共享一台物理机"的**并发、隔离、资源分配**三大问题。
- **现实对照**：xv6 的 `proc` 数组 + `struct proc`；Linux 的 `task_struct`（更复杂的进程/线程统一模型）。**边界**：真实内核还有 cgroup、namespace、调度类等，408 不考，仅作"进程抽象可扩展到容器"的直觉。

## 1. 定义与抽象 ★核心

> 覆盖：进程 vs 程序、PCB、进程五态（含挂起）、线程 vs 进程。
> 归档 → `notes/408/10-进程与线程.ipynb`

### 1.1 机制层（①）
- **进程 = 程序 + 数据 + PCB（进程控制块）**；是程序的一次执行过程。
- **进程 vs 程序**：程序静态（指令集合），进程动态（一次执行，有生命周期）。
- **PCB**：进程存在的**唯一标志**，含——进程标识、处理机状态（寄存器现场）、调度信息（状态/优先级）、内存指针、资源清单、I/O 状态。
- **进程五态**：新建 → 就绪 → 运行 → 阻塞 → 终止；扩展含**挂起**（就绪挂起、阻塞挂起）。
- 画**状态机图**（见 TOOLKIT §1.3）：
  - 就绪→运行：**被调度**
  - 运行→就绪：**时间片到 / 被抢占**
  - 运行→阻塞：**等待事件（如 I/O）**
  - 阻塞→就绪：**事件完成**
- **线程 vs 进程**：进程是**资源分配**单位，线程是**CPU 调度**单位；线程共享进程的地址空间与资源，仅私有栈与寄存器。
  - 用户级线程 vs 内核级线程 vs 组合（多对一/一对一/多对多）。

### 1.2 设计层（②）
- **为什么要区分进程/线程**：创建/切换进程开销大（要换地址空间），引入线程让**调度更轻量**，适应并发需求。
- **为什么需要 PCB**：进程被中断后要能**恢复现场**，故必须保存上下文；PCB 是"进程的档案"。
- **为什么状态要细分**：阻塞与就绪的区分在于"**缺的是 CPU 还是缺的是事件**"——这是调度决策的依据。
- **现实对照**：
  - xv6 `struct proc`（kernel/proc.h）：`enum procstate`（UNUSED/SLEEPING/RUNNABLE/RUNNING/ZOMBIE）、`context`（保存寄存器现场）、`pagetable`（地址空间）。
  - Linux `task_struct`：进程与线程**统一**为 task，通过 `clone()` 的标志位决定共享哪些资源。
  - **边界**：xv6 状态名与教材（就绪/运行/阻塞）**不完全对应**，需做名词映射（RUNNABLE≈就绪）；408 考教材术语，不考 xv6 枚举名。

### 1.3 验收层（③）
**题型清单**：

| # | 题型 | 模板要点 | 优先级 |
|---|---|---|---|
| 1 | 状态转换触发条件 | 逐个事件对应一条迁移边，区分"谁触发" | ★核心 |
| 2 | 状态数判断（含挂起） | 挂起 = 换出到外存，状态翻倍；画图逐一列 | ☆常规 |
| 3 | PCB 内容判断 | 判断某信息是否属于 PCB（如"指令序列"不属于） | ☆常规 |
| 4 | 进程 vs 线程辨析 | 从"分配单位/调度单位/共享性/开销"四维作答 | ★核心 |
| 5 | 用户级/内核级线程判定 | 看"阻塞是否导致整个进程阻塞" | ☆常规 |

- **代表例（题型1）**：某进程执行中发起 I/O 请求 → 状态如何变化？
  - 答：运行→阻塞（等待 I/O）；I/O 完成中断到来 → 阻塞→就绪（仅当**被调度**才运行→就绪→运行，注意"就绪后不会自动运行"）。
- **常见易错**：把"阻塞→运行"直接连边（**错**，必须先经就绪）；把"时间片到"当成"阻塞"。

## 2. 创建与控制 ★核心

> 覆盖：fork / exec / wait、父子进程、写时复制（COW）、进程终止。
> 归档 → `notes/408/10-进程与线程.ipynb`（COW 涉及内存，可拆一节到 `04-内存与虚拟内存.ipynb`）

### 2.1 机制层（①）
- **fork()**：创建子进程，**复制父进程**的地址空间副本；返回值——父进程得子 PID，子进程得 0，失败得 −1。
  - **父子并发执行**，执行顺序不确定。
- **exec()**：用新程序**替换**当前进程的地址空间（PID 不变）；成功不返回。
- **wait()**：父进程等待子进程结束并回收（避免**僵尸进程**）。
- **写时复制（COW）**：fork 后父子共享物理页，**只在写时才复制**，减少开销。
- **孤儿进程 vs 僵尸进程**：父先死 → 孤儿（被 init 收养）；子先死父未 wait → 僵尸。

### 2.2 设计层（②）
- **为什么要 fork + exec 分离**：`fork` 只复制、`exec` 才换程序，二者配合可**在 exec 前修改环境**（如重定向）。
- **为什么用 COW**：直接全复制太贵，绝大多数页 fork 后不会被写 → 惰性复制。
- **为什么需要 wait**：回收子进程资源，维护父子同步。
- **现实对照**：
  - xv6 `fork()`（kernel/proc.c）：分配 proc、`uvmcopy` 复制页表；`exec` 解析 ELF。
  - Linux 用 `clone()` + COW 页表项。
  - **边界**：408 常考"fork 的输出次数/继承内容"，不考内核实现细节。

### 2.3 验收层（③）
**题型清单**：

| # | 题型 | 模板要点 | 优先级 |
|---|---|---|---|
| 1 | fork 输出次数 | 数 fork 调用次数 n → 进程数 2^n；注意 printf 缓冲与换行 | ★核心 |
| 2 | 父子继承判断 | 继承：文件描述符表、环境变量、信号处理；不继承：PID、返回值 | ★核心 |
| 3 | fork+exec+wait 组合 | 按语句顺序画进程树 | ☆常规 |
| 4 | COW 计数 | 统计写操作触发几次复制 | ☆常规 |
| 5 | 僵尸/孤儿判定 | 看父子退出顺序与是否 wait | ☆常规 |

- **代表例（题型1）**：`fork(); fork();` 后有几个进程？→ 4 个（2^2）。
- **变式**：`if(fork()==0) fork();` 后几个进程？→ 3 个（父1 + 子fork出的2）——**注意只有子进程再 fork**。
- **常见易错**：忽略"子进程从 fork 返回处继续执行"；忽略 printf 缓冲区未刷新导致输出重复。

## 3. 调度 ★核心

> 覆盖：三级调度、调度时机、FCFS/SJF/HRRN/RR/优先级/多级反馈队列、调度性能计算、实时调度。
> 归档 → `notes/408/11-调度.ipynb`

### 3.1 机制层（①）
- **三级调度**：高级（作业，外存→内存）、中级（换入换出，内外存）、低级（进程，就绪→运行）。408 主要考**低级调度**。
- **调度时机**：进程终止、阻塞、时间片到、更高优先级到达（抢占）、I/O 中断等。
- **抢占式 vs 非抢占式**：抢占 = 运行中可被打断；非抢占 = 主动放弃才切换。
- **典型算法**：
  - **FCFS**（先来先服务）：简单，对短作业不利。
  - **SJF/SPF**（短作业优先）：平均等待最短（理论上最优），但需预知运行时间、可能饥饿。
  - **HRRN**（高响应比优先）：响应比 = (等待+服务)/服务，兼顾长短作业。
  - **RR**（时间片轮转）：公平、响应快，性能依赖时间片大小。
  - **优先级调度**：可抢占/不可抢占，有饥饿问题（老化解决）。
  - **多级反馈队列（MLFQ）**：多就绪队列 + 不同时间片 + 逐级下降 + 定期提升。
- **甘特图**（见 TOOLKIT §1.1）：横轴时间、纵轴进程，画横条标起止。

### 3.2 设计层（②）
- **为什么需要调度**：CPU 是稀缺共享资源，需在多道程序间**分配**，兼顾**效率（吞吐/利用率）与公平（响应/等待）**。
- **策略与机制分离**：调度器（策略）与上下文切换（机制）解耦。
- **为什么 RR 时间片要折中**：太大→退化为 FCFS；太小→切换开销占比高。
- **为什么 MLFQ 兼顾**：短作业（交互）快速完成，长作业逐级降但不会饿死。
- **现实对照**：
  - xv6 `scheduler()`（kernel/proc.c）：简单的**时间片轮转**遍历 RUNNABLE 进程。
  - Linux **CFS**：完全公平调度，用 **vruntime（虚拟运行时间）+ 红黑树**选最小 vruntime 者。
  - **边界**：CFS 的 vruntime 计算、组调度 408 不考；只用于理解"公平调度"思想。

### 3.3 验收层（③）
**题型清单**：

| # | 题型 | 模板要点 | 优先级 |
|---|---|---|---|
| 1 | 甘特图推演 | 按算法画时间轴 → 标各进程完成时刻 | ★核心 |
| 2 | 计算周转/等待/带权周转/响应时间 | 四公式分别列（见 TOOLKIT §2） | ★核心 |
| 3 | 算法对比（同作业集） | 逐个算，列表比较平均周转/等待 | ★核心 |
| 4 | RR 时间片敏感性 | 换时间片重推，观察切换次数与等待变化 | ☆常规 |
| 5 | 抢占 vs 非抢占差异 | 关键看"到达时刻能否抢占当前进程" | ★核心 |
| 6 | MLFQ 队列迁移 | 按规则逐级降/定期升，画队列状态 | ☆常规 |
| 7 | HRRN 响应比计算 | 响应比 =(等待+服务)/服务，选最大 | ☆常规 |

- **代表例（题型2）**：三进程 A/B/C，到达 0/1/2，服务 3/2/1，用 SJF（非抢占）算平均周转。
  - 模板：画甘特图 → 逐个求完成时刻 → 周转=完成−到达 → 求平均。
- **变式**：同作业集改用 RR（时间片=1），重算平均周转并比较。
- **常见易错**：到达时刻忘记参与排序；带权周转 = 周转/服务（不是服务/周转）；抢占式忘记"到达即可能打断"。

## 4. 同步与互斥 ★核心

> 覆盖：临界区、信号量、PV 操作、管程、经典问题（生产者-消费者/读者-写者/哲学家进餐）。
> 归档 → `notes/408/12-同步与互斥.ipynb`

### 4.1 机制层（①）
- **临界区**：访问临界资源的那段代码；需保证**互斥**进入。
- **同步 vs 互斥**：同步 = 有序协作（有先后依赖）；互斥 = 争用同一资源（同时只能一个）。
- **信号量**：`P(S)`（wait，S-- 后 <0 则阻塞）、`V(S)`（signal，S++ 后 ≤0 则唤醒）。
- **经典问题**：
  - 生产者-消费者：`mutex`(互斥) + `empty`/`full`(同步)。
  - 读者-写者：读优先/写优先/公平。
  - 哲学家进餐：死锁规避（限定人数/奇偶取筷/AND 信号量）。
- **管程（Monitor）**：封装共享变量与操作，**语言级**保证互斥（条件变量 wait/signal）。

### 4.2 设计层（②）
- **为什么要信号量**：提供"**阻塞/唤醒**"机制，比忙等（自旋）高效，是通用同步原语。
- **为什么 P/V 要原子**：否则多进程并发修改 S 会竞态。
- **为什么管程优于信号量**：把同步**结构化**，减少人为 P/V 顺序错误。
- **现实对照**：
  - xv6：`sleep()` / `wakeup()`（kernel/proc.c）+ 自旋锁 `spinlock`。
  - Linux：`futex`（快速用户态互斥）、`mutex`、`semaphore`。
  - **边界**：408 考"信号量/PV 代码正确性"，不考 futex 实现。

### 4.3 验收层（③）
**题型清单**（PV 七类）：

| # | 题型 | 核心关系 | 优先级 |
|---|---|---|---|
| 1 | 生产者-消费者（单/多缓冲） | 互斥 + 同步 | ★核心 |
| 2 | 读者-写者（读/写优先/公平） | 互斥 + 计数 | ★核心 |
| 3 | 哲学家进餐 | 死锁规避 | ★核心 |
| 4 | 纯互斥（N 进程争 1 资源） | 互斥 | ☆常规 |
| 5 | 前驱/执行顺序约束 | 同步 | ★核心 |
| 6 | 资源计数分配 | 计数信号量 | ☆常规 |
| 7 | 综合变式（独木桥/理发师/黑白棋…） | 组合 | ☆常规 |

**通用五步模板**：
1. **数进程**：列出所有并发进程。
2. **找关系**：互斥→信号量初值 1；同步（有先后）→初值 0；资源计数 N→初值 N。
3. **定信号量**：给每个关系起名、定初值。
4. **排 PV 位置**：P 放在"进入临界区/等待条件"前，V 放在"离开/条件满足"后。
5. **查错**：初值对不对？**P 顺序会不会死锁**？会不会饥饿？

- **代表例（题型1）**：生产者-消费者（缓冲区 N）。

```c
semaphore mutex = 1;   // 互斥访问缓冲区
semaphore empty = N;   // 空位数量
semaphore full  = 0;   // 产品数量

producer() {                    consumer() {
    while(1) {                      while(1) {
        produce_item();                 P(full);    // 等产品
        P(empty);   // 等空位            P(mutex);   // 进临界区
        P(mutex);   // 进临界区          get_item();
        put_item();                      V(mutex);   // 出临界区
        V(mutex);   // 出临界区          V(empty);   // 空位+
        V(full);    // 产品+          }
    }                           }
}
```
  - **关键**：`P(empty)` / `P(full)` 必须在 `P(mutex)` **之前**，否则缓冲区满/空时**抱着 mutex 死等** → 死锁。
- **变式（负向考法）**：题目给出把 `P(mutex)` 放在 `P(empty)` 之前的代码，问"何时死锁"——答：缓冲区满时生产者持 mutex 等 empty，消费者等 mutex 无法释放，**死锁**。
- **常见易错**：漏设同步信号量（只用 mutex）；V 顺序无所谓但 P 顺序敏感；读者写者忘记计数器本身的互斥。

## 5. 死锁与资源分配 ☆常规

> 覆盖：死锁四条件、处理策略（预防/避免/检测/解除）、银行家算法、资源分配图。
> 归档 → `notes/408/13-死锁.ipynb`

### 5.1 机制层（①）
- **死锁四必要条件**：互斥、请求并保持、不可剥夺、循环等待。
- **处理策略**：
  - **预防**：破坏四条件之一（如资源有序分配破坏循环等待）。
  - **避免**：动态检查（**银行家算法**，找安全序列）。
  - **检测与解除**：资源分配图化简；解除 = 剥夺/撤销/回退。
- **资源分配图**：圆 = 进程，方框 = 资源类，**请求边/分配边**；无环→无死锁；有环→可能死锁（每类资源单实例时有环即死锁）。
- **银行家算法**：维护 Available / Max / Allocation / Need；找**安全序列**。

### 5.2 设计层（②）
- **为什么预防代价大**：破坏条件往往牺牲资源利用率（如一次性申请全部资源）。
- **为什么银行家算法"避免"而非"预防"**：不改规则，而是**每次分配前判断**是否会导致不安全态。
- **现实对照**：xv6 无死锁避免机制（教学简化）；Linux 靠**锁序规范 + 检测工具**（lockdep）。
- **边界**：408 考银行家算法的手算，不考 lockdep。

### 5.3 验收层（③）
**题型清单**：

| # | 题型 | 模板要点 | 优先级 |
|---|---|---|---|
| 1 | 资源分配图判死锁 | 画图 → 找环 → 判断（单实例有环即死锁） | ★核心 |
| 2 | 银行家算法安全性检查 | 列 Available/Need → 找安全序列 | ★核心 |
| 3 | 银行家算法——能否分配 | 试分配 → 检查新状态是否安全 | ★核心 |
| 4 | 四条件判断 | 给场景判断违反了哪个条件 | ☆常规 |
| 5 | 最小资源数（不死锁） | 用公式推最少资源数 | ☆常规 |

- **代表例（题型2）**：给定 Available=[3,3,2]、各进程 Max/Allocation，求 Need → 逐步找安全序列（如 P1→P3→P4→P0→P2）。
- **变式（题型3）**：请求 Request=[1,0,2] 能否分配给 P1？→ 试分配后重找安全序列，找得到则安全。
- **常见易错**：Need = Max − Allocation 算错；安全序列不唯一，找**任一**即可，不必找唯一。
